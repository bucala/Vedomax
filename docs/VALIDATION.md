## Repeat local database checks

On a Docker-capable machine, use a disposable container without a published port. Local trust authentication is solely for the isolated test fixture; never use it in production.

```sh
docker run -d --name vedomax-db -e POSTGRES_HOST_AUTH_METHOD=trust postgres:17
docker exec vedomax-db pg_isready -U postgres
# Wait for readiness before executing the following commands.
docker exec -i vedomax-db psql -U postgres -v ON_ERROR_STOP=1 < supabase/tests/bootstrap.sql
docker exec -i vedomax-db psql -U postgres -v ON_ERROR_STOP=1 < supabase/migrations/202610260001_core.sql
docker exec -i vedomax-db psql -U postgres -v ON_ERROR_STOP=1 < supabase/seed.sql
docker exec -i vedomax-db psql -U postgres -v ON_ERROR_STOP=1 < supabase/tests/security.sql
docker rm -f vedomax-db
```

The auth harness is for a fresh ordinary PostgreSQL database only, never a real Supabase instance. Docker daemon routing and proxy/CA configuration must follow the cloud runtime skill when using a managed cloud environment.
